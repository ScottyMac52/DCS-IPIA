# Tested application releases

Every PR/main CI run builds a self-contained Windows release candidate after the shared .NET quality gates, Windows solution/tests/WPF smoke, and layout/theme/inventory checks pass. The candidate's actual executable initializes an isolated database, opens the main window, validates shipped hardware and exercises native PNG rendering. The packaging script silently installs setup.exe into a temporary folder, verifies every installed payload hash, starts the installed application, uninstalls it, then extracts and starts the portable ZIP. Candidate artifacts are uploaded with source commit/test evidence and SHA-256 checksums.

To publish a new application version, update the four-component version in `release/version.json` and the release notes in a reviewed PR. Merging the version change to main runs the complete release gates again on that exact commit and publishes the exact tested assets with a new tag. Explicit four-component tag pushes remain supported. Existing tags/releases are rejected for merged release requests, and existing releases are never replaced. The shared quality workflow remains authoritative for independent per-layer coverage; repository packaging adds exact installer tests not provided by the existing shared installer workflow.

Startup checks use the explicit `--release-smoke <isolated-folder>` diagnostic option; normal startup continues using the user's local data. Each diagnostic run records success/failure in its own folder and exits. These automated checks establish application/packaging behavior; they do not establish manual controller behavior in DCS or complete DCS-Common consumer parity.
