# Huey release acceptance

The reference is the actual DCS-UH-1H-Huey v3.1.1 release, not output generated by IPIA itself. Its authorized workflow artifact (run 35558158045, artifact 10620389932) was downloaded and verified against SHA-256 `b98da84ab465987091e76902e0017d2f3fd424d99e7af3d7ae6d84730dd921fb`. The inner OvGME archive hashes to `3a4b6a33f8676e2e1872505791938fbb08f8e3ec641c8a74e3b6569b57b06421`; Complete hashes to `cc2b5abca2513c41c1db23c04757b9d7a72aad97e23afb1d1b165ab87562e48b`.

Sources are pinned at consumer commit `77d924cce220355860e8f026cff3524bac531e29`. The source MIT license, captured reference file hashes and release provenance are in `tests/Dcs.Ipia.Tests/Fixtures/HueyParity/PROVENANCE.json`. All 54 source/reference files are independently checked against recorded SHA-256 and length, with no unlisted fixture files allowed. Fixtures are historical test evidence, never deployed as generated IPIA output. Original machine paths remain historical evidence; import does not follow them.

`HueyReleaseAcceptanceTests` uses the real imported consumer metadata, five physical profiles (including three distinct MFDs), actual bundled SVGs and shared Lua, the editor's mapped assignment projection, captured authored labels and reviewed original integration guide. It saves and reopens SQLite, freezes version 3.1.1, verifies Complete, compares repeated bytes, restores into an empty SQLite database, changes a page and restores the earlier snapshot into another empty database. Restore must reproduce the original OvGME and Complete bytes while leaving the edited workspace intact. No mutable checkout, DCS installation or external Common repository is used during snapshot rebuild.

## Measured differences

| Output | Comparison and interpretation |
| --- | --- |
| Five aircraft Lua profiles | Exact parsed command IDs, added/changed/removed dispositions, physical keys, modifier chords and axis filters. Formatting and display-name spelling are not a native binding change. |
| Aircraft and UI modifiers | Every released name/device/key/mode must remain present. Native device-name reconciliation and automatic keyboard declarations can add valid entries. |
| Released MFD3 UI profile | Four shifted functions move and 32 bindings are added with the current pinned Common defaults. The exact delta is checked in `Fixtures/HueyUiLayerChanges.json` and included in the generated report. This is a reviewable difference, not exact native parity. |
| Other UI device profiles | IPIA materializes the applicable captured shared UI profiles. The old release deployed only MFD3; generated archive entries list these additions. |
| Six kneeboard PNGs | All six old/current pages are 1200 × 1600 with exact six output names and valid rendered images; the report records legacy/current dimensions and SHA-256 for every page. Different renderer/layout/text means these are not byte-identical legacy PNGs. CI uploads all six generated pages for visual review. |
| Summary SVG | Historical release contains the rendered summary SVG; IPIA deploys kneeboard PNGs. Editable geometry is captured in the portable snapshot rather than deployed as a summary SVG. |
| Documentation | IPIA generates consolidated installation, control mapping, provenance and integration guidance rather than copying legacy per-device Markdown. The original OPENKNEEBOARD-VAICOM guide must survive verbatim inside INTEGRATIONS. The report lists generated guide names. |
| Complete archive | Separate OvGME, generated Documentation and portable Snapshot plus version metadata/checksums; old distribution paths are intentionally replaced by the existing IPIA distribution contract. Independent verification regenerates the output from captured inputs. |
| Clean rebuild and rollback | Restored snapshots reproduce the IPIA archive bytes exactly. Equality is within the same renderer/platform, not a claim that old browser and current Skia encoders match. |

Visual inspection also reveals crowding/overlapping UI text on MFD3. This is an unresolved visual acceptance item; successful encoding and matching dimensions do not establish legible labels. Other observed differences include modifier color/legend wording, authored graphic metadata and removal of the old source-build footer. None is hidden behind an exact PNG parity claim.

The old release's MOZA-shifted MFD3 pause moves from JOY_BTN24 to JOY_BTN13, active pause from JOY_BTN13 to JOY_BTN18, left hand from JOY_BTN27 to JOY_BTN21 and right hand from JOY_BTN21 to JOY_BTN27. Additional AVA and VKB modifier chords account for 28 added bindings; the four relocated bindings account for the other four. The source's abstract UI utilization is resolved through the current captured template. Importing those old abstract sources with today's default catalog is therefore a migration, not an identical native UI configuration. Do not declare an identical Huey cutover without accepting or correcting this delta.

## Reproduce and review

Run `dotnet test tests/Dcs.Ipia.Tests --filter FullyQualifiedName~HueyReleaseAcceptanceTests`. Set `IPIA_PARITY_OUTPUT` to a new report directory if desired; otherwise output goes to the temporary `ipia-huey-parity` directory. The report contains native changes, page dimensions/hashes, archive paths, documentation names, snapshot/archive digests and restore/rollback results. Windows CI uploads it with the generated PNGs as `huey-release-parity`. Full CI retains independent six-layer 80% line and branch gates and actual Windows release-candidate checks.

See [application completion](application-completion.md) for the revised scope. These measured UI changes and visual review are explicit acceptance items. They do not justify adding draw.io source creation or legacy repository scaffold generation back to the application finish line.
