# Issue #323 — PR 1A: Squadrons capability reconciliation

## Purpose and provenance

Bring the **validated native and application capabilities** from the protected Squadrons development branch into the shared architecture **before** designing the shared diagram / assignment views. Do not port the existing monolithic Squadrons WPF window or overwrite shared drawing/scrolling infrastructure.

Frozen source for this reconciliation: `fix/squadrons-controller-associations` at `18babcc6134d2fb7adb362765aef3646b410e37e`. Base: `main` at `44cac811208db3a2348835cc0e13830b729560d6`, which includes #324, #325 and #326. The protected original branch is unchanged.

## Migrated application and simulator behavior

- Optional application ports `INativeAxisPairEditor` and `INativeRecordCreator` derive from `INativeRecordEditor`; `ISimCapturedDeviceLinks` makes capture-specific operations explicit rather than relying on generic Elite or DCS semantics.
- `GameProfileSession` stages these native operations through its existing isolated-snapshot/edition/hardware-verification boundary. It also supports reviewed capture changes (clear one/all, move/remove unused slots), preserving foreign profile identities and preventing stale review application.
- Squadrons native backend and source document support verified creation, explicit record selection, **atomic +/- axis reassignment**, conflicts on already-used physical axes, lossless source retention and native slot reordering/clear with round-trip validation.
- Squadrons catalog, assignment planner/target, command filters, system-control decoder, drawing projection and workspace projection form simulator-owned **application data**, not presentation event handlers. The shared drawing component can consume `SquadronsDrawingProjection` in PR 2.
- Characterization tests copied from the preserved source branch cover native records, conflicts, verification, read-only system records, command discovery/filtering, control-key mapping and no-mutation guarantees.

## Deliberately not migrated (deferred to PR 2 / PR 3)

- `SquadronsWorkspaceWindow.xaml` and `.xaml.cs` changes (including a one-off command browser / drawing surface and obsolete context actions).
- `EliteDiagramPresenter` modifications and other shared WPF/Elite/DCS changes from the Squadrons branch.
- `DiagramViewport.cs` from the Squadrons branch: main already owns the canonical #326 wheel policy (wheel = vertical, Shift = horizontal, Ctrl = pointer zoom).
- All changes in the protected War Thunder branch.

This is a **capability integration PR, not complete Squadrons UI parity**. The existing mainline Squadrons table view continues functioning and can consume these richer interfaces when shared UI composition is implemented.

## Migration constraints for next PRs

1. The shared presenter displays controls from `UiLayerDiagram` and callouts generated by adapter-owned projections; it does not encode Squadrons-native numeric `axis/button/deviceid` fields.
2. Any whole-axis action must use `GameProfileSession.RebindNativeAxisPair` (where supported), not a WPF-side loop that can stage half an axis.
3. Native record creation uses `INativeRecordCreator` only for verifiable concepts. Never manufacture undocumented native IDs.
4. Clearing native captured assignments requires an explicit reviewed operation and a disambiguated record; unsupported actions must not appear as functioning context-menu items.
5. Diagram scroll/zoom is owned by the shared `DiagramViewport`; avoid duplicating handlers from the older Squadrons branch.
6. Selected native device, physical controller identity, section filter, selected command and pending state remain distinct application/UI state, as demonstrated by the user-provided inconsistency video.
7. Preserve game-specific features behind capability registration; a table-only mode must remain supported.
